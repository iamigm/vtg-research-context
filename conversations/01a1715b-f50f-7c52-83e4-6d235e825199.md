## 2026-10-25T04:41:03.986Z — Codex final report

Qwen3-VL-Thinking을 말하는 거라면, **reasoning에서 시각적 근거를 언급하는 구간과 최종 답을 결정하는 구간**의 attention을 우선 추천해. pilot의 목적을 “모델이 추론 과정에서 이미지의 어디를 참조하는지 확인”하는 것으로 가정한 제안이야.

먼저 추출 대상은 **LLM decoder의 text query → visual key attention**으로 잡으면 돼. Qwen3-VL에서는 이미지 표현이 텍스트와 함께 decoder에 들어가므로, self-attention 행렬에서 해당 부분을 추출하는 방식이야. [공식 구현](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py)

| 우선순위 | 선택할 토큰·구간 | 확인할 내용 |
|---|---|---|
| **1** | **시각적 관찰을 진술하는 구간**: 객체명, 색상, 위치, 숫자, OCR 문자열 | “빨간 자동차”, “왼쪽에 3개”라는 진술이 관련 이미지 영역을 참조하는가? |
| **2** | **최종 답의 핵심 구간**: 선택지, 클래스명, 숫자, 답변 대상 | 답을 결정할 때 이미지와 앞선 reasoning 중 어디를 참조하는가? |
| **3** | **비교·관계 판단 구간**: “왼쪽”, “더 크다”, “같다”, “두 개” | 판단에 필요한 여러 영역을 함께 참조하는가? |
| **4** | **재검토·수정 전후 구간**: “다시 보면”, “아니”, “하지만”과 뒤따르는 관찰 | 재검토 발화 전후로 시각적 참조가 실제로 달라지는가? |
| **5** | **reasoning 전체에서 일정 간격으로 뽑은 토큰** | 의미 기반으로 고른 구간만 보는 선택 편향 없이, 추론 진행에 따른 변화를 볼 수 있는가? |

**단어 하나보다는 의미 있는 span을 선택하는 편이 좋아.** 예를 들어 `왼쪽에 빨간 자동차가 두 대 있다`에서 `자동차`만 보기보다, 객체·속성·개수를 포함하는 span의 토큰별 attention과 평균을 함께 보는 거야. 서브워드로 나뉘는 경우에도 덜 민감해져. `<think>`, `</think>`, 줄바꿈은 구간 경계용으로 저장하되, 주 분석 대상으로 삼을 필요는 없어.

특히 **“그 토큰을 생성할 때”와 “그 토큰 위치에서”의 attention을 구분해야 해.** causal decoder에서 전체 시퀀스의 토큰 `x_t`를 생성하는 logits는 직전 위치 `t−1`에서 나와.

- **`x_t`를 생성할 때 참조한 곳**을 보려면: query 위치 `t−1`.
- **이미 입력된 `x_t`의 표현이 참조하는 곳**을 보려면: query 위치 `t`.

따라서 생성 단계의 attention을 저장하면서 새로 생성된 토큰에 붙일 때는 이 정렬 기준을 명시해야 해. [Qwen3-VL causal LM 구현](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py)

내가 pilot을 설계한다면 다음처럼 저장하겠어.

- **전체 생성 토큰:** 이미지·질문·이전 reasoning으로 향하는 attention 합계. 추론 흐름을 보는 작은 요약값이야.
- **위 표의 주요 span:** visual token 전체에 대한 공간 attention map. 가능하면 layer/head 정보를 유지하고, 평균은 시각화할 때 계산.
- **최종 답 span:** 이미지뿐 아니라 앞선 reasoning token으로 향하는 attention도 저장. 어떤 관찰 문장을 참조하는지 함께 확인.
- **정렬 정보:** 원본 token IDs, span 위치, query 위치, 이미지 토큰 위치와 이미지 grid 정보.

공간 map에는 **이미지로 향한 attention 총량도 반드시 함께 기록**하는 게 좋아. 이미지 영역 안에서만 재정규화하면, 실제로는 이미지에 거의 attention을 주지 않은 경우에도 선명한 heatmap이 나올 수 있거든.

예산이 제한적이면 **① 첫 시각적 관찰, ② 답을 뒷받침하는 핵심 관찰, ③ 최종 답** 세 구간부터 시작하는 걸 추천해. 다만 attention은 참조 패턴을 보여주는 지표라서, 그것만으로 해당 영역이 답의 원인이라고 단정하지는 말고, 흥미로운 사례에 한해 영역 가림 실험으로 확인하면 좋아.

## 2026-10-25T04:54:32.686Z — Codex final report

일반적인 Multi-Head Attention에서는 **두 번째 설명이 맞아.** Q/K/V를 각각 hidden dimension 크기로 projection한 뒤, 그 결과를 head별로 나눠 사용해. 다만 **각 head가 원본 hidden state의 일부만 보는 것은 아니야.** 각 head의 projection은 원본 hidden state 전체를 입력으로 받아.

토큰 하나의 hidden state를 \(x\in\mathbb{R}^{d_{\text{model}}}\), head 수를 \(H\), head dimension을 \(d_h\)라 하면:

\[
d_{\text{model}}=H d_h
\]

일반적인 MHA의 projection은 다음과 같아.

\[
q=xW_Q,\quad k=xW_K,\quad v=xW_V,
\qquad W_Q,W_K,W_V\in\mathbb{R}^{d_{\text{model}}\times d_{\text{model}}}
\]

즉, **합쳐진 Q/K/V projection은 차원을 유지**해. 이후 각각을 head별로 나눠:

\[
q=[q_1;\ldots;q_H],\qquad q_h\in\mathbb{R}^{d_h}
\]

하지만 이것은 head별 projection을 따로 정의하는 것과 수학적으로 같아.

\[
W_Q=[W_Q^{(1)}\;\cdots\;W_Q^{(H)}],
\qquad q_h=xW_Q^{(h)}
\]

여기서 \(W_Q^{(h)}\in\mathbb{R}^{d_{\text{model}}\times d_h}\)이므로, **head 하나의 관점에서는 전체 입력을 작은 차원으로 projection**하는 셈이야. 구현에서는 이 연산들을 큰 행렬곱 하나로 묶은 뒤 reshape하는 경우가 일반적이야.

각 head는 자신의 attention 분포로 **자신의 V 벡터들을 가중합**해 \(d_h\)차원 출력을 만들어. query 위치 \(t\)에 대해:

\[
a^{(h)}_{t,s}
=\operatorname{softmax}_{s}
\left(\frac{q_t^{(h)}\cdot k_s^{(h)}}{\sqrt{d_h}}\right),
\qquad
o_t^{(h)}=\sum_s a^{(h)}_{t,s}v_s^{(h)}
\]

마지막에는 head 출력들을 **이어 붙이고(concatenate), output projection으로 섞어**:

\[
o_t=
\underbrace{[o_t^{(1)};\ldots;o_t^{(H)}]}_{d_{\text{model}}\text{ 차원}}
W_O,\qquad
W_O\in\mathbb{R}^{d_{\text{model}}\times d_{\text{model}}}
\]

따라서 head별 출력을 평균내는 구조는 아니고, 이어 붙인 뒤 학습된 \(W_O\)로 head 간 정보를 결합하는 구조야. 이 출력이 이후 residual 경로에 더해져.

지금 사용하는 **Qwen3-VL-8B는 일반 MHA 대신 GQA**라서 K/V 차원에는 차이가 있어. 앞서 확인한 로컬 설정은 hidden dimension 4,096, query head 32개, KV head 8개, head dimension 128이야.

| 단계 | Qwen3-VL-8B의 차원 |
|---|---|
| Q projection | \(4096\rightarrow4096=32\times128\) |
| K/V projection 각각 | \(4096\rightarrow1024=8\times128\) |
| attention 계산 | query head 4개가 하나의 KV head를 공유 |
| head별 출력 | query head마다 128차원, 총 32개 |
| concatenate → output projection | \(4096\rightarrow4096\) |

즉, **이 모델은 Q는 차원을 유지하고 K/V는 축소하지만, attention 분포와 출력은 query head 32개 기준**이야. 그래서 앞서 attention 저장량을 계산할 때도 KV head 8개가 아니라 **32개**를 사용한 거야.

## 2026-10-25T04:58:02.499Z — Codex final report

**한 layer · 한 head · 한 query 토큰**의 attention 분포는, 참조하는 **key 토큰 수만큼의 값**을 저장하면 돼.

\[
\text{용량}=\text{key 토큰 수}\times\text{값 하나의 바이트 수}
\]

이번 pilot의 **첫 생성 토큰**은 입력 10,370개를 참조하므로:

| 저장 정밀도 | 전체 key 10,370개 | 영상 key 10,010개만 |
|---|---:|---:|
| BF16 / FP16 (2바이트) | **20,740 B ≈ 20.25 KiB** | **19.55 KiB** |
| FP32 (4바이트) | **41,480 B ≈ 40.51 KiB** | **39.10 KiB** |

생성이 진행되면 이전 생성 토큰도 key에 추가돼서 조금씩 커져. **head dimension 128은 곱하지 않아.** Attention weight는 query–key 토큰 쌍마다 스칼라 하나이기 때문이야.

특정 key 하나에 대한 attention 값만 말한 거라면 **2바이트 또는 4바이트**야.

## 2026-10-25T04:59:12.408Z — User

모든 저장은 불가능한데 어떤 방식을 추천해? 평균을 내는 과정에서 왜곡이 걱정되거든?


## 2026-10-25T04:59:59.297Z — Codex final report

평균으로 head 정보를 없애기보다는, **모든 layer·head·생성 토큰을 유지하면서 key 축을 압축**하는 걸 추천해. 지금처럼 영상 구간을 찾는 실험이라면 **시간별 attention 합계 + 개별 key의 top-k + 일부 원본 분포** 조합이 좋아.

평균에 대한 걱정은 타당해. 예를 들어 두 head가 각각 영상 초반과 후반에 집중하면, 평균에서는 두 구간을 모두 보는 것처럼 나타나. 어느 head도 갖지 않은 패턴이 생기는 거지. 반면 **head별 데이터를 보존하면 나중에 평균·최댓값·head 간 차이를 선택해서 분석**할 수 있어.

**1. 기본 저장: head별 시간 분포**

각 layer·head·query 토큰에서, **같은 시간 bin에 속한 영상 patch의 attention을 합산**해:

\[
A_{\ell,h,t,b}=\sum_{k\in\text{시간 bin }b} A_{\ell,h,t,k}
\]

이번 영상은 시간 bin이 35개이고 영상 key가 10,010개였으니, 영상 분포를 **10,010개 값 → 35개 값**으로 줄일 수 있어.

- 유지: 모든 layer·head, reasoning 토큰별 변화, 시간 구간별 attention 총량.
- 소실: 같은 시간 bin 안에서 **화면의 어느 위치**를 봤는지.
- 영상 내부에서 다시 합이 1이 되도록 정규화하지 말고, **원래 attention 값을 합산**해서 저장.

이 합산은 시간 bin에 할당된 attention mass를 정확히 보존해. 다만 “공간적으로 같은 패턴”까지 보존하는 것은 아니야.

**2. 보완 저장: 각 분포의 top-k key와 원래 weight**

각 layer·head·query마다 attention이 큰 key의 **위치와 weight**를 저장해. 초기값으로 `k=128` 정도를 시도하되, 적절한지는 저장되는 mass로 판단하면 돼.

반드시 함께 저장할 값은:

- `topk_indices`, `topk_weights`
- `retained_mass = sum(topk_weights)`
- `residual_mass = 1 - retained_mass`

**top-k만 다시 정규화하면 안 돼.** 원래 전체 attention의 20%만 담은 top-k가 100%인 것처럼 보이게 되거든. 분포가 넓게 퍼진 head는 top-k로 잘 표현되지 않으므로, `retained_mass`가 낮으면 그 사실을 분석에 반영해야 해.

전체 key에서 top-k를 뽑으면 영상 key가 거의 안 남는 경우도 있어. 공간 분석이 필요하면 **영상 key와 텍스트 key에 별도 예산**을 주고, 각각의 원래 weight를 보존하는 편이 좋아.

**3. 텍스트 참조도 별도로 보존**

최종 답변이 어떤 reasoning 구간을 참조하는지 보려면 영상만 저장해서는 부족해. 이번처럼 trace가 짧다면 **이전 reasoning·답변 key에 대한 분포는 그대로 저장**하고, 입력 텍스트는 질문·지시문·특수 토큰별 mass를 함께 기록하는 구성이 유용해.

| 분석 목적 | 저장할 데이터 |
|---|---|
| 추론 중 영상의 언제에 주목하는가? | head별 시간 bin 합계 |
| 그 시점의 화면 어디에 집중하는가? | 영상 patch top-k |
| 답이 어떤 reasoning을 참조하는가? | 이전 생성 토큰에 대한 원본 분포 |
| 압축으로 중요한 패턴을 놓치는가? | 일부 query의 전체 key 원본 분포 |

마지막 원본 분포는 **균일 간격으로 선택한 query + 핵심 관찰·최종 답 구간**에 대해 저장하는 걸 권해. 핵심 단어만 고르면 선택 편향이 생길 수 있어서 두 방식을 섞는 거야.

내가 이번 pilot에 적용한다면 **모든 layer·head를 유지하고, 시간 bin 합계는 FP32, top-k와 선택한 원본 분포도 가능하면 FP32로 저장**하겠어. 먼저 소수 샘플에서 원본과 비교해 top-k의 보존 mass와 시간 분포가 맞는지 확인한 다음 전체로 확대하면, 평균으로 인한 head 간 혼합을 피하면서 무엇을 잃었는지도 명확히 알 수 있어.

k/v 축을 압축하는다는 게 무슨 말이야?


## 2026-10-25T05:03:00.943Z — Codex final report

내가 말한 건 **모델의 K/V 벡터를 압축한다는 뜻이 아니라, 계산된 attention 분포에서 ‘참조 대상 토큰 축’을 줄여 저장한다는 뜻**이야. 정확히는 **attention의 key 축을 압축**한다고 해야 해.

한 layer·head에서 attention 행렬은 다음 형태야:

\[
A\in\mathbb{R}^{T_{\text{query}}\times T_{\text{key}}}
\]

- **행(query)**: 지금 분석하는 reasoning·답변 토큰
- **열(key)**: 그 토큰이 참조하는 영상·질문·이전 생성 토큰
- **원소**: 해당 query가 해당 key에 주는 attention weight 하나

예를 들어 reasoning의 `medicine` 토큰이 영상 patch 10,010개를 참조한다면:

```text
                 영상 patch key 10,010개
medicine query → [0.001, 0.003, 0.0002, ...]
```

내가 제안한 저장 방식은 이 **10,010개 열**을 다음처럼 줄이는 거야.

**시간별 합산:** 같은 시간 bin에 속한 patch들의 weight를 합쳐 35개 값으로 저장.

```text
10,010개 patch weight → 35개 시간 bin의 attention 총량
```

“영상의 언제를 봤는가”는 남지만, 그 시간의 “화면 어디를 봤는가”는 사라져.

**Top-k 저장:** 10,010개 중 weight가 큰 128개의 **원래 위치와 값**만 저장하고, 나머지는 총합을 기록.

```text
10,010개 weight → [(patch 위치, weight) × 128] + 나머지 mass
```

이 경우 큰 weight의 공간 위치는 남지만, 나머지 patch 사이의 세부 분포는 사라져.

**두 방식 모두 모델 내부의 Q/K/V나 attention 계산, 출력에는 손대지 않아. 계산 결과를 디스크에 어떤 형태로 남길지만 바꾸는 거야.** KV cache 압축과는 별개의 이야기야.

**처음에는 초반·중반·후반을 고르게 포함한 6개 레이어를 저장하는 걸 추천해.** 지금 모델에서 어느 레이어가 유용한지는 아직 측정하지 않았으니, 특정 구간에만 집중하기보다 비교 가능한 구성을 만드는 게 좋아.

| 구간 | 추천 레이어 | 확인할 질문 |
|---|---|---|
| 초반 | **L0, L7** | 영상·입력 질문·이전 생성 토큰 사이의 attention 배분이 어떻게 시작되는가? |

| 후반 | **L28, L35** | 출력에 가까운 단계에서는 어떤 정보에 attention이 집중되는가? |

이건 **구간별 역할을 미리 단정하는 선택이 아니라, 깊이에 따른 변화를 관찰하기 위한 균등 표집**이야. 마지막 레이어만으로 판단하면 앞선 레이어에서 이미 전달된 시각 정보를 놓칠 수 있어. 특히 후반의 직접적인 영상 attention이 작다고 해서 영상 정보를 사용하지 않았다는 뜻은 아니야.

내가 이번 실험을 구성한다면 이렇게 하겠어.

- **36개 전체 레이어:** head별로 `영상 / 입력 질문 / 기타 입력 / 이전 reasoning / 이전 답변 / 현재 위치`에 대한 **attention mass 합계**를 저장. 작은 요약값으로 레이어별 변화를 확인.
- **선택한 6개 레이어:** 네가 정한 head 압축을 적용하고, **모든 key 토큰에 대한 상세 분포**를 저장.
- 이후 요약값에서 특징적인 변화가 나타난 레이어를 상세 저장 대상으로 추가.

전체 레이어의 요약값은 **head를 평균하지 않고 남기는 것**을 추천해. 그러면 상세 분포에서 head를 압축하더라도, 영상에 집중하는 소수 head가 있었는지는 확인할 수 있어.

| 레이어당 저장 분포 수 | BF16 / FP16 | FP32 |
|---|---:|---:|
| 1개 | 16.85 MiB | 33.69 MiB |
| 4개 | 67.39 MiB | 134.77 MiB |
| 8개 | 134.77 MiB | 269.54 MiB |

따라서 시작점으로는 **전체 36개 레이어의 head별 범주 합계 + L0·7·14·21·28·35의 상세 분포**가 좋아. 저장량을 제한하면서도 레이어를 잘못 골라 중요한 패턴을 놓쳤는지 확인할 여지가 남아.
