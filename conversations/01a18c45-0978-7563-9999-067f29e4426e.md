GT oracle의 annotation 취득 비용은 추론 비용과 별도다.\n\n기본 조건 네 개 × 100 final = 400회, Random seed 43/44 추가 = 200회, 공통 scout 100회로 **최대 700개 응답**을 계획한다. 기존 scout 재사용은 입력 pixels·IDs·timestamps·grid·모델·generation config가 모두 검증될 때만 허용한다. 재사용이면 GPU 신규 실행 수를 차감하되 논리적 두 단계 비용은 차감하지 않는다. final Uniform은 재실행하여 같은 입력의 반복 안정성도 측정한다.\n\n## 6. 프레임 선택 알고리즘 v1\n\n사전 고정값: global anchor 비율 0.5, focus window 길이 0.4T, random planner seeds 42/43/44. 성능을 본 뒤 이 값을 고르지 않는다.\n\n### 6.1 공통 후보 집합\n\n영상별 원본 PTS(time base 포함)와 source frame ID로 후보 집합 C_i를 만든다. **기존 8fps metadata의 실제 프레임과 기존 2fps baseline 프레임의 합집합**을 사용한다. 서로 같은 source frame은 중복 제거한다. 기존 2fps가 8fps의 부분집합이라고 가정하지 않는다. 후보는 원본 timestamp순이다.\n\n저장된 8fps 실행이 768 cap 때문에 충분하지 않으면 원본 영상에서 8fps 요청 규칙의 후보를 새로 추출한다. 이는 모델 입력 프레임 수를 늘리는 것이 아니라 CPU 후보 준비이며, 이를 source metadata와 구분하고 비용을 기록한다. 원본 fps가 8 미만이면 존재하는 프레임만 사용한다. 보간으로 영상을 만들지 않는다.\n\n공통 decoder·frame map을 먼저 확정한다. 후보 원본 RGB를 한 번 준비해 조건들이 같은 frame ID에 대해 같은 pixel hash를 읽게 한다. sparse seek별 차이가 생기면 전체 조건을 같은 순차 decoding으로 새 run에서 생성하고, 과거 응답은 historical reference로만 둔다. 8fps 응답·trace는 새 샘플 조합의 응답으로 재사용할 수 없다.\n\n### 6.2 조건별 계획\n\n| 조건 | 선택 규칙 | GT 사용 |\n|---|---|---|\n| Uniform | 기존 2fps ordered frame IDs를 정확히 재현 | 없음 |\n| Random-guided | 동일 anchors + 원본 전체에서 무작위 중심인 고정 폭 window에 집중 | 없음 |\n| GT-guided | 동일 anchors + GT midpoint 중심의 고정 폭 window | 위치 계획에만 사용 |\n| Pred-guided | 동일 anchors + uniform scout 첫 구간 midpoint 중심의 고정 폭 window | 없음 |\n\n알고리즘은 다음과 같다.\n\n1. F_i개 baseline frames에서 `A_i=floor(F_i/2)`개를 고른다. 인덱스 `round(j*(F_i-1)/(A_i-1))`, j=0..A_i-1로 양 끝을 포함하며 ties는 작은 source ID 우선이다. A_i<2 같은 특수 영상은 preflight에서 별도 처리 규칙을 확정한다.\n2. GT·Pred의 중심은 각각 첫 유효 구간의 `(s+e)/2`를 [0,T]에 제한한다. **위치 계획에 한해서만** clamp한다. 평가 예측은 clamp하지 않는다.\n3. window 폭은 모든 조건에서 `w=0.4T`다. 중심 주변 [c-w/2,c+w/2]가 영상 밖이면 폭을 유지하며 [0,T] 안으로 이동한다. GT와 Pred의 길이를 사용하지 않아 위치 비교에 길이 정보가 추가되지 않게 한다.\n4. Random은 `u~Uniform(0,1)`에서 c=uT로 정하고 같은 이동 규칙을 쓴다. seed는 SHA-256(`run_id|sample_key|planner_seed`)의 앞 8 byte를 big-endian 정수로 변환해 독립 RNG를 만든다. Python built-in hash는 사용하지 않는다.\n5. anchors를 제외한 C_i의 window 내부 프레임을 시간순으로 배열하고, `K_i=F_i-A_i`개를 균등한 rank quantile로 선택한다. n>=K이면 인덱스 `floor((j+0.5)*n/K)`를 쓴다. n<K면 전부 선택한다.\n6. 부족한 수는 아직 선택하지 않은 C_i 중 window까지의 시간 거리가 작은 순서(동률 source ID)로 채운다. fill 수·비율을 기록한다. anchors와 focus를 union하여 실제 source ID 중복 없이 정확히 F_i개를 확보하고 timestamp순으로 정렬한다.\n7. 후보가 F_i보다 적으면 중단한다. baseline 원본 자체에 padding/중복이 있는 경우에는 유일 관측과 processor padding을 분리한 예산 정책을 preflight에서 해결해야 하며, 임의로 중복 추가하지 않는다.\n8. Pred scout가 parse fail, 비유한 값 또는 s>=e이면 **Uniform으로 fallback**한다. 평가에서 실패 표본을 삭제하거나 GT로 보정하지 않는다. 범위 밖이지만 유효한 구간은 위 중심 clamp를 적용하고 횟수를 별도 보고한다.\n\nGT-guided가 실제 GT 양 경계를 항상 포함하는 설계는 아니다. 짧은 고정 window의 효과를 보는 위치 oracle이며, 엄밀한 최적 allocation 상한이 아니다. boundary coverage가 낮으면 그 자체를 해석에 반영한다. 추가 GT-boundary sampler나 폭 탐색은 v2로 분리한다.\n\n### 6.3 비균일 시간 표현: 필수 구현 gate\n\n선택된 프레임을 연속된 “가짜 2fps/8fps 영상”처럼 전달하면 프레임 내용과 시간이 뒤틀린다. **원본 source PTS/indices와 video duration이 native processor의 timestamp/temporal position 경로에 반영되는지 코드로 확인해야 한다.**\n\n- prepare_pair에서 frame decode 이후, resize/processor 이전에 ordered frame IDs와 PTS를 주입할 수 있는 최소 adapter를 추가한다.\n- installed processor의 실제 metadata contract를 읽는다. `fps=8` 하나로 비균일 배열의 시간을 표현하지 않는다. temporal patch가 복수 프레임을 합치는 경우 그룹별 timestamp 산정도 저장한다.\n- 선택 배열과 timestamp block의 대응을 검사하고, text timestamp token IDs·temporal position 관련 값·grid·attention mask를 input.json에 보존한다.\n- uniform을 adapter에 통과시켰을 때 기존 경로와 pixels/input IDs/grid/positions가 같은지 먼저 검사한다.\n- 같은 pixel 배열에 PTS만 알려진 값으로 바꾼 synthetic probe에서 입력의 시간 표현이 예상대로 바뀌는지 확인한다. 이후 누락·역순·중복 PTS를 거부하는지도 검사한다.\n- 설치 버전이 비균일 시각을 안전하게 표현할 수 없으면 본 실험을 중단한다. 임의 metadata key를 만들지 않는다. 명시적 frame timestamp를 넣는 다른 입력 형식을 쓰려면 네 조건과 uniform bridge를 모두 새 run으로 만들고 기존 입력과 달라진 점을 보고한다.\n\n## 7. 구현·실행 순서와 산출 계약\n\n아래 CLI는 **구현해야 할 제안 인터페이스**다. 현존하는 run.py subcommand라고 해석하지 않는다.\n\n```bash\ncd /home1/irteam/experiments/zero-shot\n.venv/bin/python _lib/adaptive_temporal_sampling.py preflight --config results/adaptive_temporal_sampling_pilot_v1/config.json\n.venv/bin/python _lib/adaptive_temporal_sampling.py plan --config results/adaptive_temporal_sampling_pilot_v1/config.json\n.venv/bin/python _lib/adaptive_temporal_sampling.py smoke --config results/adaptive_temporal_sampling_pilot_v1/config.json\n.venv/bin/python _lib/adaptive_temporal_sampling.py run --config results/adaptive_temporal_sampling_pilot_v1/config.json\n.venv/bin/python _lib/adaptive_temporal_report.py --run-dir results/adaptive_temporal_sampling_pilot_v1\n```\n\n1. **Preflight:** 서버 경로·환경·evaluator 소스·registry·모델 revisions·100개 mapping·2/8fps 출처·time representation을 검증한다. hash manifest를 원자적으로 확정한다.\n2. **Scout:** 기존 동일 입력 예측 재사용 가능성을 확인한다. 불일치면 공통 입력 경로에서 100개를 생성한다. GT는 로드하지 않는다.\n3. **Plan:** scout와 고정 seed로 Uniform/Random/Pred 계획을 먼저 저장·hash한다. 격리된 GT planner가 GT 계획을 추가한다. final 답변 생성 전 계획을 freeze한다.\n4. **Smoke:** 성능과 무관하게 sample ID 순 첫 5개에서 모든 조건과 반복 Uniform을 실행한다. 시간 표현, RGB/cache, 예산, 저장·resume 검사를 한다. 통과한 정확한 산출물은 본 실행에 재사용할 수 있다.\n5. **Run:** 단일 모델·처음에는 batch=1로 실행한다. 조건 순서는 GT와 독립적인 ID 기반 회전으로 교차하여 시간대 영향을 줄인다. GPU 중복 작업을 점검한다. 기존 background 실행·진행 로그 관례를 따른다.\n6. **Report:** 모든 primary final 400개 및 random sensitivity 200개를 확인하고 평가한다. 완료 전 일부 표본으로 go/no-go를 바꾸지 않는다.\n\nOOM 때 특정 조건만 grid/F를 줄이지 않는다. batch/worker 등 출력 불변이 입증된 운영 설정만 변경할 수 있고 변경 기록을 남긴다. 입력 또는 generation 설정이 바뀌면 새 run이다.\n\n완료 파일은 temp→atomic rename으로 저장한다. 재개 key는 `run_id,config_hash,cohort_hash,sample_key,condition,planner_seed,input_hash`다. 기존 complete hash가 일치하는 항목만 건너뛴다. 응답이 생성됐는데 분석만 실패했으면 원본 응답으로 복구하고 재생성하지 않는다.\n\n## 8. 평가와 통계\n\n### 8.1 기존 평가 코드와의 정합성\n\n공용 TimeLens `extract_time`을 import해 첫 예측 구간과 단일 GT를 채점한다. 실제 함수 위치·소스 hash와 evaluator CLI를 preflight에서 resolve한다. 보고서에 이름만 등장한 Python 구현을 임의로 “공식 코드”라고 복제하지 않는다.\n\n주평가는 **raw seconds, no round, no clipping**이다. 파싱 실패는 IoU=0으로 100개 전체에 포함한다. 정상 구간의 tIoU는 교집합 길이 / 합집합 길이다. 길이 0·역전·비유한 구간은 0점으로 정의하고 개수를 기록한다. 범위 초과 유효 구간은 clipping 없이 채점한다. 여러 예측이면 첫 구간만 사용하며 다중 구간 빈도를 보고한다. EOS 미도달도 자동 제외하지 않고 파싱 가능한 첫 구간은 평가한다.\n\n호환성 표는 기존 Python `round`(ties-to-even)와 기존 parser fallback 규칙을 그대로 적용해 따로 산출한다. raw/rounded 지표·분모·parser 버전을 컬럼으로 명시한다. GT의 원문 값도 보존한다.\n\n출력 문자열 fixture는 소수·정수·음수·HH:MM/MM 지원 형식·다중 구간·빈 응답·역전·범위 초과·파싱 실패·512-token 잘림을 포함한다. 설치된 evaluator와 독립 IoU 계산을 대조한다. 2fps 같은 100개 raw 기준선이 보고서의 46.90%/48%를 반올림 표시 수준에서 재현하는지 확인하고, 다르면 legacy/full/decoder/평가 규칙을 추적한다. 새 입력 경로로 baseline이 달라졌다면 이전 점수를 억지로 맞추지 않고 새 Uniform을 주기준으로 삼는다.\n\n### 8.2 필수 지표\n\n| 종류 | 지표·분모 |\n|---|---|\n| 주지표 | query별 paired ΔIoU 및 평균 ΔmIoU(pp): GT−Uniform, Pred−Uniform |\n| 대조 | Random42−Uniform, GT−Random42, Pred−Random42. Random43/44와 seed 평균은 사전 지정 sensitivity |\n| Grounding | raw mIoU, R@1 IoU≥.3/.5/.7, 전체 100개 기준 |\n| 변화 | IoU 개선/악화/동일, .5 실패→성공/성공→실패, 예측 구간 동일 비율 |\n| 경계 | start/end 절대 오차 평균·중앙값·P90(초), T로 정규화한 오차. 두 조건 모두 유효한 쌍에서 paired 차이를 계산하고 해당 N/실패 수 명시 |\n| 실패 | parse fail, s>=e, 비유한, 범위 초과, 다중 구간, EOS 미도달, fallback, infra failure |\n| 샘플링 | 실제 frame 수/유일 frames/padding, B, H/W/grid, 실제 간격 min/median/max, window 내 frames, fill 비율, 원본 후보의 fps/cap |\n| 비용 | CPU decode/resize/plan, GPU prefill/generate, 총 wall time·peak VRAM, 출력 토큰. scout/final·cold/warm cache·재사용 분리 |\n\n파싱 실패가 경계 오차 표에서 빠지는 선택 효과를 보완하려고 `boundary_within_1s/2s`(양 endpoint 모두 만족)를 전체 100개로 계산하고 실패는 false로 센다. infra failure는 모델 0점으로 숨기지 않으며, 미완료로 남겨 전체 완료 판단을 보류한다.\n\n### 8.3 Evidence coverage 진단\n\n실제 유일 관측 시각 집합 S에 대해 사전 고정 ε=0.5초로 다음을 계산한다. 단순히 GT 안의 프레임 비중이 높다는 것을 사건 coverage와 혼동하지 않는다.\n\n- **GT frame fraction:** GT 안의 유일 frames / 전체 유일 frames.\n- **Temporal coverage:** GT와 `union([t−ε,t+ε],t∈S)`의 교집합 길이 / GT 길이.\n- **Boundary coverage:** start/end 각각 `min_t |t−boundary|≤ε`, 두 경계 동시 coverage, 최소 거리(초).\n- 위 값을 전체 frames와 focus-only frames에서 각각 계산한다. anchors로 이미 관측된 경계와 신규 관측을 구분한다.\n- scout IoU별, GT 길이/T별, baseline B_i별, fill/fallback별 breakdown은 사후 진단임을 표시하고 N을 함께 쓴다.\n\nGT coverage 진단은 final 생성이 끝난 뒤 evaluator에서만 계산한다. coverage가 개선되고 답변이 그대로인 것은 “관측 추가가 생성 개선으로 연결되지 않은 사례”이지 이해가 완료되었다는 증명은 아니다.\n\n### 8.4 불확실성\n\n기본 paired bootstrap 20,000회, seed=42, 95% percentile CI. **video ID 단위 cluster resampling**으로 같은 영상의 query를 함께 뽑고 각 replicate에서 query 가중 평균 Δ를 다시 계산한다. 네 조건과 random seeds에 같은 재표집을 적용한다. n_query=100과 n_video를 모두 보고한다. random seed 평균은 query마다 세 결과를 평균한 뒤 집계한다. 300개 random 응답을 독립 query로 세지 않는다.\n\n2개 주비교와 여러 보조비교의 CI는 탐색적이며 다중비교 보정 없는 확증 검정이라고 표시하지 않는다. seed 변동성, 새 영상 일반화 및 다른 모델 일반화를 포함하지 않는다. ### 2. GT 안팎의 프레임 예산

GT 길이에 관계없이 일정한 비율의 프레임을 몰아주면 긴 GT에서 문제가 생겨. 따라서 **프레임 수의 비율이 아니라, 초당 프레임 수의 비율**을 고정하자.

제안은 **GT 안을 밖보다 3.5배 촘촘하게** 보는 것이야. 기존 설계가 집중 구간 40%에 약 70%의 프레임을 배치하려던 것과 같은 밀도 비율이야. 검증된 최적값은 아니므로 실행 전에 고정하고 결과에 따라 바꾸지 않아.

영상 길이가 \\(T\\), GT 길이가 \\(L\\), 총 프레임 수가 \\(F\\)라면:

\\[ F\_{\text{GT 안}} =\operatorname{round}\left(F\frac{3.5L}{3.5L+(T-L)}\right) \\]

나머지를 GT 밖에 배치해.

총 60장을 보여주는 경우의 예시는 다음과 같아.

| GT가 영상에서 차지하는 비율 | GT 안 | GT 밖 |
| ---------------- | ---- | ---- |
| 10%              | 17장  | 43장  |
| 40%              | 42장  | 18장  |
| 80%              | 56장  | 4장   |
| 100%             | 60장  | 0장   |

### 3. 구간 안팎에서 각각 균등하게 배치

- **GT 안:** 구간을 배정된 프레임 수만큼 같은 길이로 나누고, 각 칸의 중심 시각에서 프레임을 선택해.
- **GT 밖:** GT 앞부분과 뒷부분을 이어 붙인 시간축에서 같은 방법으로 선택하고, 이를 원래 영상 시각으로 되돌려.

이렇게 하면 GT 앞뒤에도 **같은 밀도**를 적용하면서, 각 부분의 길이에 따라 프레임 수가 배분돼. 앞뒤에 무조건 절반씩 나누는 방식은 아니야.

예를 들어 30초 영상에서 GT가 6\~18초이고 예산이 60장이라면:

- GT 안 12초에 42장: 목표 간격 약 **0.286초**.
- GT 밖 18초에 18장: 목표 간격 **1초**.
- 바깥 예산은 앞쪽 6초에 6장, 뒤쪽 12초에 12장.

실제 영상에서는 존재하는 원본 프레임 중 골라야 하므로 간격이 완벽히 같지는 않아. **같은 원본 프레임을 중복 선택하지 않고, 실제 간격이 목표와 얼마나 다른지 기록**해야 해.

각 질문에서:

2. 영상 안에서 길이 \\(L\\)인 구간의 시작점을 무작위로 고른다.
3. 그 구간 안팎에 GT 조건과 같은 밀도 비율로 프레임을 배치한다.

Random은 미리 정한 세 seed로 반복하자.

**1. 추가 추론 전에, 무엇이 바뀐 질문에서 좋아졌는지 확인하자.**

질문마다 Uniform과 GT 전체 집중을 나란히 놓고 다음을 정리해.

- 새로 들어온 프레임은 무엇인가?
- 빠진 프레임은 무엇인가?
- 예측이 다른 사건에서 정답 사건으로 이동했는가?
- 같은 사건을 가리키면서 시작·종료만 조정됐는가?
- 원래 답과 거의 같은가?

여기서는 **사건을 잘못 고른 오류**와 **사건은 맞게 골랐지만 범위를 잘못 정한 오류**를 나누는 게 중요해. 두 오류는 비슷한 IoU 개선으로 나타나도 필요한 해결책이 달라.

사례는 좋은 것만 고르지 말고, 데이터셋별로 개선·악화·불변 사례를 고정된 방식으로 추출하자. 사람이 프레임을 보고 라벨링할 때는 가능하면 모델의 개선 여부를 가리고, 일부는 두 사람이 독립적으로 판단해. “이 프레임이 결정적이다”라는 판단을 결과에 맞춰 붙이지 않기 위해서야.

**2. 첫 추가 실험은 ‘추가’와 ‘제거’를 분리하자.**

현재 GT 전체 8배 계획에서 질문별로 다음 두 집합을 그대로 가져와.

- \(I\): Uniform에는 없고 GT 집중에 새로 들어온 프레임
- \(O\): Uniform에는 있었지만 GT 집중에서 빠진 프레임

새 sampler를 만들 필요 없이 다음 네 입력을 만들 수 있어.

| 조건 | 입력 | 확인하려는 것 |
|---|---|---|
| 기존 Uniform | \(U\) | 기준 |
| 추가만 | \(U \cup I\) | 기존 관측을 유지해도 새 프레임이 도움이 되는가? |
| 제거만 | \(U \setminus O\) | 새 증거 없이 일부 관측을 빼는 것만으로 좋아지는가? |
| 추가와 제거 | \((U \setminus O)\cup I\) | 현재 GT 집중 결과 |

이 표는 **원인 분해용**이야. ‘추가만’은 입력 예산이 늘고 ‘제거만’은 줄어들므로, 동일 비용의 성능 비교라고 주장하면 안 돼. 공간 해상도를 고정하고 실제 프레임·토큰 수를 기록해야 해.

해석은 이렇게 할 수 있어.

- **추가만으로 개선:** 새 관측이 도움이 됐다는 근거.
- **제거만으로 개선:** 기존 관측 중 일부가 예측을 방해했을 가능성.
- **추가만은 좋지만 추가·제거는 덜 좋음:** 빼낸 프레임에도 필요한 맥락이 있었을 가능성.
- **추가·제거를 함께 해야 개선:** 두 변화의 상호작용 가능성.

다만 제거 효과를 곧바로 ‘방해 사건 제거’라고 부르면 안 돼. 입력이 짧아진 효과일 수도 있어. **같은 수의 프레임을 무작위로 추가하거나 제거하는 대조군**을 함께 두자. 위치도 시간대별로 가능한 한 맞추면 더 좋아.

**3. 새 프레임이 도움이 됐다면, ‘한 장의 증거’인지 ‘변화 과정’인지 나누자.**

여기서 Evidence recovery와 Temporal disambiguation을 구분해.

먼저 새 프레임을 사람이 다음처럼 표시해.

- **행동 단서:** 도구 접촉, 물체를 놓는 순간처럼 행동을 식별하는 모습
- **전후 상태:** 행동 직전과 직후의 상태
- **진행 과정:** 행동이 이어지거나 다른 행동으로 전환되는 모습

그다음 같은 추가 프레임 수로 비교해.

| 추가 관측 | 질문 |
|---|---|
| 행동 단서 중심 | 특정 모습만 새로 보여줘도 개선되는가? |
| 전후 상태·진행 과정 중심 | 행동의 변화 과정을 보여줘야 개선되는가? |
| 사건 내부 균등 | 특별히 고르지 않아도 관측을 늘리면 충분한가? |

**행동 단서 몇 장만으로 효과가 재현되면 Evidence recovery 쪽**, 전후 상태와 진행 과정이 있어야 효과가 유지되면 **Temporal disambiguation 쪽** 근거가 강해져.

단, 이것도 완전히 배타적인 분류는 아니야. 전후 상태 자체가 결정적인 증거일 수 있어. **특정 프레임을 뺐을 때 효과가 사라지는지, 다시 넣으면 회복되는지**까지 확인하면 해석이 더 단단해져.

**4. ‘방해 사건’ 가설은 사건 외부 프레임을 구분해서 검증하자.**

정답 밖의 프레임을 모두 방해물로 취급하면 안 돼. 필요한 배경이나 사건 전후 맥락일 수도 있어.

- 질문과 비슷해서 혼동할 수 있는 다른 행동
- 질문과 관련이 적은 배경
- 정답을 이해하는 데 필요한 맥락

**정답 내부 관측은 고정하고**, 같은 수의 외부 프레임을 각 종류에서 제거해 비교해. 비슷한 다른 행동을 제거했을 때 특히 좋아지고, 그 행동을 다시 넣으면 나빠진다면 Distractor suppression에 더 직접적인 근거가 돼.

- 동일한 입력 화면 크기와 전처리 규칙 적용

\[
\text{프레임 묶음당 공간 토큰 예산}
\approx
\frac{\text{영상 전체 토큰 예산}}{\text{시간축 프레임 묶음 수}}
\]

그래서 같은 2fps라면:

| 영상 | 선택되는 프레임 | 공간 해상도에 쓸 여유 |
|---|---|---|
| 짧은 영상 | 적음 | 상대적으로 큼 |
| 긴 영상 | 많음 | 상대적으로 작음 |

**Qwen이 권장하는 것은 상황에 맞게 입력량을 조절하는 것이야.**

공식 문서는 GPU 메모리와 용도에 따라 프레임별 `min_pixels`, `max_pixels`를 정하도록 안내해. `qwen-vl-utils`의 영상 전체 예산인 `total_pixels`는 입력이 과도하게 길어지는 것을 피하려고 **`24576 × 32 × 32` 미만**을 권장해. 이는 운영상 권장값이고, 모델이 그 이상을 받을 수 없다는 뜻은 아니야. **우리의 14,336은 이 권장값과도 다른 실험 설정**이야. **프레임당 예산을 고정하면 필요한 전체 예산은 이렇게 늘어나.**

현재 모델은 인접한 두 프레임을 묶어 처리하므로, 공간 토큰 수를 \(S\), 프레임 수를 \(F\)라고 하면:

\[
B_{\text{영상}}\approx \left\lceil\frac{F}{2}\right\rceil S
\]

예를 들어 **두 프레임 묶음당 공간 토큰을 360개로 고정**한다면:

| 입력 프레임 수 | 필요한 영상 토큰 수 |
|---:|---:|
| 60장 | 10,800개 |
| 300장 | 54,000개 |
| 600장 | 108,000개 |

텍스트·timestamp·특수 토큰은 여기에 추가돼. 이 계산은 공식 모델 설정의 시간축 압축과 공간 병합 규칙에 따른 예시야. [Qwen3-VL-8B 설정](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct/blob/main/config.json)

**GPU 외에도 확인해야 할 한계가 있어.**

mIoU는 정답과 예측 구간의 겹침률을 질문별로 평균한 값입니다. 높을수록 좋고, pp는 백분율 차이입니다. GT는 정답 전체 구간에 8배 밀도로 집중하는 조건이며, Random은 두 seed 평균입니다.

| 데이터셋 | 공간 설정 | Uniform mIoU | GT mIoU | GT−Uniform | GT−Random |
|---|---|---:|---:|---:|---:|
| Charades | 낮음 | 44.63% | 47.13% | **+2.50pp** | +7.02pp |
| Charades | 높음 | 46.55% | 47.65% | **+1.10pp** | +5.15pp |
| ActivityNet | 낮음 | 48.69% | 53.24% | **+4.55pp** | +8.03pp |
| ActivityNet | 높음 | 51.12% | 54.95% | **+3.82pp** | +7.42pp |
| QVHighlights | 낮음 | 58.85% | 61.95% | **+3.11pp** | +4.43pp |
| QVHighlights | 높음 | 60.21% | 63.99% | **+3.79pp** | +5.12pp |

- **GT는 여섯 경우 모두 Random보다 좋았고**, 그 차이의 영상 단위 bootstrap 95% 신뢰구간도 모두 0보다 높았습니다.
- Uniform 대비 개선은 **Charades의 높은 설정**과 **QVHighlights의 낮은 설정**에서 신뢰구간이 0을 포함했습니다.
- 공간 예산을 높였을 때 Uniform은 세 데이터셋 모두 점수가 올랐습니다. 하지만 **GT 집중의 추가 이득이 커졌다고 볼 근거는 없었습니다.** 그 이득의 high−low 차이는 세 데이터셋 모두 신뢰구간이 0을 포함합니다.

**2. 더 엄격한 IoU 기준에서도 좋아졌나?**

아래는 **GT−Uniform 성공률 차이**입니다. 성공률은 IoU가 해당 기준 이상인 질문의 비율이며, 0.7이 가장 엄격합니다.

| 데이터셋 | 공간 설정 | IoU≥0.3 | IoU≥0.5 | IoU≥0.7 |
|---|---|---:|---:|---:|
| Charades | 낮음 | +3.33pp | +2.67pp | +2.33pp |
| Charades | 높음 | +2.00pp | **0.00pp** | +1.33pp |
| ActivityNet | 낮음 | +4.67pp | +5.67pp | +4.00pp |
| ActivityNet | 높음 | +4.67pp | +5.00pp | +4.00pp |
| QVHighlights | 낮음 | +4.67pp | +6.67pp | +2.00pp |
| QVHighlights | 높음 | +2.67pp | +8.00pp | +3.00pp |

Charades는 평균 겹침률뿐 아니라 성공률에서도 개선이 작습니다. ActivityNet과 QVHighlights는 세 기준 모두 개선 방향입니다. 이 표의 양수 자체가 각각 통계적으로 확실하다는 뜻은 아닙니다.

**3. GT 비율과 영상 길이를 나누면 평균에서 가려진 차이가 보입니다**

높은 공간 설정에서 **GT 비율이 5% 미만**인 질문의 GT−Uniform mIoU 변화는 다음과 같습니다.

| 데이터셋 | 질문 수 | 개선 |
|---|---:|---:|
| Charades | 60 | **+4.93pp** |
| ActivityNet | 67 | **+6.80pp** |
| QVHighlights | 60 | **+10.65pp** |

Charades도 작은 사건에서는 이득이 있습니다. 반면 ActivityNet은 GT 비율 40% 이상에서 **−8.73pp**로 악화됐습니다.

두 축을 함께 보면 단순히 “긴 영상일수록 좋다”도 아닙니다. 예를 들어 **ActivityNet·GT 비율 5% 미만**에서도:

- 영상 120–180초: **+12.96pp**, 20개
- 영상 180초 이상: **−3.19pp**, 17개

작은 집단이라 확정적 해석은 어렵지만, GT 비율 하나만으로 모든 차이를 설명할 수도 없습니다.

**제 해석은 이렇습니다.** 기존 Charades의 높은 공간 해상도는 절대 성능에 기여했을 가능성이 있습니다. 그러나 공간 예산을 맞춘 뒤에도 시간 집중의 이득이 다른 데이터셋 수준으로 뚜렷하게 커지지는 않았습니다. 따라서 **공간 해상도 차이만으로 기존 현상을 설명하기는 어렵고, 사건이 차지하는 비율과 영상 길이·내용을 함께 봐야 합니다.**
