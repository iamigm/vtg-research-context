## 2026-10-07T08:06:52.282Z — Codex final report

**입력 구성과 query 프롬프트는 TimeLens 공식 저장소의 Qwen baseline 평가 코드를 그대로 사용했습니다.** 다만 **TimeLens 모델에 적용한 별도의 timestamp 변환이나 학습 방법을 Qwen에 추가한 것은 아닙니다.**

실제 입력 순서는 다음과 같습니다. `<prefill>`, `<query>`라는 special token을 넣지는 않았습니다.

```text
[모델 기본 chat template]

user:
    [전체 영상에서 샘플링한 영상 토큰]

    Please find the visual event described by the sentence '{query}',
    determining its starting and ending times.
    The format should be:
    'The event happens in <start time> - <end time> seconds'.

assistant:
    [여기서부터 답변 생성]
```

위 문구의 `{query}`에 벤치마크의 이벤트 문장을 넣었습니다. 두 모델·두 데이터셋 모두 같은 프롬프트입니다. 실제 구현은 [공식 코드의 GROUNDER_PROMPT와 messages 구성](/home/irteam/analysis/failure_mode/failure_cases/vendor/TimeLens/evaluation/utils.py:8)에 있습니다.

말씀하신 `<prefill>`을 **query 이전에 들어가는 영상·문맥 부분**이라는 의미로 보면, 다음처럼 처리했습니다.

| 항목 | 실제 처리 |
|---|---|
| 영상 | 전체 영상을 대상으로 **2 FPS** 샘플링 |
| 해상도 예산 | `min_tokens=64`, `total_tokens=14336` |
| Qwen2.5-VL 시간 정보 | 기본 영상 처리와 시간 기반 positional encoding 사용. 프레임 앞에 timestamp 문장을 별도로 삽입하지 않음 |
| Qwen3-VL 시간 정보 | 기본 processor가 시간 메타데이터로 `<t seconds>`와 영상 토큰을 교차 배치 |
| 추가 문맥 | 별도 caption, 영상 요약, 예시, GT timestamp 입력 없음 |

기본 chat template도 유지해서 Qwen2.5에는 기본 system 문구인 `You are a helpful assistant.`가 붙고, Qwen3에는 별도의 system message가 없습니다.

또한 **영상만 먼저 prefill하고 나중에 query를 별도 호출한 구조는 아닙니다.** 영상과 위 query 프롬프트를 한 번에 `model.generate()`에 전달했습니다. 따라서 연산 단계로서의 *prefill*에는 **영상과 query 전체가 포함**됩니다.

논문과의 관계를 정확히 말하면, **TimeLens 논문의 Qwen baseline 평가 입력 조건을 따른 것**입니다. 논문 Appendix G에도 Qwen 평가에 2 FPS, `min_tokens=64`, `total_tokens=14336`을 명시합니다. [논문 Appendix G](https://arxiv.org/html/2512.14698v1#A7)

다만 전체 데이터·실행 환경까지 맞춘 재현은 아니므로, **“입력 프로토콜은 공식 baseline을 따랐다”와 “논문 성능을 재현했다”는 구분해야 합니다.**

## 2026-10-08T06:52:08.323Z — Codex final report

**네. Qwen3-VL은 기본적으로 timestamp를 시각 토큰과 함께 입력받습니다.** 표준 video processor가 프레임 인덱스와 원본 FPS로 시간을 계산하고, 각 시각 토큰 블록 앞에 `<12.3 seconds>` 같은 **텍스트 토큰**을 자동으로 넣습니다. 기존 baseline에도 이것이 들어갔습니다. [Qwen3 processor 구현](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/models/qwen3_vl/processing_qwen3_vl.py)

정확히는 원본 프레임 하나마다 붙이는 것이 아니라, **시간축으로 합쳐지는 두 프레임의 시각 토큰 블록마다** 붙입니다. timestamp는 두 프레임 시간의 평균입니다.

TimeLens는 **7B와 8B를 구분해야 합니다.**

| 항목 | Qwen3 기본 / 공식 TimeLens-8B 입력 경로 | TimeLens-7B의 변환 방식 |
|---|---|---|
| 기반 모델 | Qwen3-VL | Qwen2.5-VL |
| 시각 블록 구성 | 서로 다른 두 프레임 `[f0, f1]` | 한 프레임을 복제한 `[f0, f0]` |
| 서로 다른 프레임의 빈도 | 이번 설정에서 2 FPS | 약 1 FPS |
| timestamp 기준 | 두 프레임 시간의 평균 | 선택한 한 프레임의 시간 |
| 시간 표기 | `<12.3 seconds>` | `12.3s:` |
| 입력 modality | video | 독립 image |
| timestamp 설명 지시문 | 기본 grounding prompt | 설명 문구를 추가 |

TimeLens 논문의 독립 이미지·프레임 복제 방식은 Appendix B.2에 설명되어 있습니다. **공개 evaluator에서는 TimeLens-8B와 Qwen3를 같은 native video 처리 분기로 보내고, TimeLens-7B만 별도 처리합니다.** [논문 B.2](https://arxiv.org/html/2512.14698v1#A2.SS2), [공식 evaluator](https://github.com/TencentARC/TimeLens/blob/5d2110fb3faf74f4b0fc5957cd7ab73bea4763dc/evaluation/utils.py)

따라서 **우리가 추가 실행한 Qwen3 “timestamp 변환” 실험은, 이미 timestamp를 받는 Qwen3에 TimeLens-7B의 입력 방식을 이식한 ablation**입니다. 공식 TimeLens-8B 입력 재현이나, timestamp 유무 비교가 아닙니다. 프레임 내용·시간 기준·표기·지시문이 함께 바뀌었습니다.

위치 인코딩 설명도 바로잡으면, **Qwen3는 기본 상태에서도 절대 시간을 텍스트로 표현**합니다. 공간 위치 인코딩은 유지하지만, Qwen2.5처럼 절대 시간을 temporal position ID로 전달하는 방식과는 다릅니다. 그래서 이번 Qwen3 실험을 “시간 MRoPE 제거 효과”로 해석해서도 안 됩니다. 보고서에도 이 구분을 반영했습니다. [Qwen3 위치 인코딩 구현](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py#L923)

**복제는 한 프레임을 ‘독립 이미지’로 처리하기 위한 구조적 장치입니다.** 그리고 서로 다른 프레임을 약 1 FPS로 줄인 것은 기존 비디오 처리와 비용을 맞추려는 선택입니다.

Qwen의 vision encoder는 기본적으로 **연속된 두 프레임을 temporal patch embedding에서 합쳐 하나의 시각 토큰 블록**으로 만듭니다. 단순 평균이 아니라 학습된 연산입니다.

```text
기본 비디오 입력, 2 FPS:

프레임 시각       0.0초   0.5초   1.0초   1.5초
시각 토큰 블록   [E(f0, f1)]     [E(f2, f3)]
```

따라서 블록 하나에 서로 다른 두 시점의 정보가 들어갑니다. 블록 앞에 timestamp를 붙여도 두 프레임 각각에 따로 붙일 수는 없습니다. Qwen3는 이 블록에 두 프레임의 평균 시간을 붙입니다.

TimeLens의 해당 실험은 **한 프레임의 시각 정보와 그 프레임의 timestamp를 직접 대응**시키려고 독립 이미지 입력을 사용합니다. 그런데 같은 encoder가 두 프레임짜리 입력을 요구하므로, 이미지 한 장을 두 번 넣습니다. Qwen의 일반 이미지 처리도 이 방식을 사용합니다.

```text
TimeLens-7B식 입력, 서로 다른 프레임 약 1 FPS:

0.0s: [E(f0, f0)]
1.0s: [E(f2, f2)]
```

이렇게 하면 각 블록의 시각 정보가 한 시점에만 대응합니다. 논문은 이를 통해 기존 비디오 시간 위치 인코딩과 textual timestamp 방식을 비교하고, 1 FPS를 사용해 다른 방식의 2 FPS 처리와 비용을 맞췄다고 설명합니다. [논문 Appendix B.2](https://arxiv.org/html/2512.14698v1#A2.SS2)

**말씀한 “그럴 바에는 더 많은 실제 프레임을 쓰자”는 직관은 타당합니다.** 다만 두 선택을 구분해야 합니다.

| 선택 | 같은 해상도에서 초당 시각 블록 수 | 특성 |
|---|---:|---|
| 기본 2 FPS, 서로 다른 프레임 두 장 결합 | 약 1개 | 두 시점의 변화 정보를 포함 |
| TimeLens식 1 FPS, 각 프레임 복제 | 약 1개 | 한 시점과 timestamp가 직접 대응 |
| TimeLens식 2 FPS, 각 프레임 복제 | 약 2개 | 더 촘촘한 시점, 시각 토큰도 약 2배 |

마지막 방식은 충분히 가능한 대안입니다. 다만 **전체 토큰 예산을 유지하려면 프레임당 해상도를 줄이는 등의 조정이 필요합니다.**

그래서 이 설계에는 분명한 손실도 있습니다. 프레임 사이 움직임과 짧은 이벤트를 놓칠 수 있습니다. **논문의 선택은 비용을 맞춘 시간 인코딩 비교를 위한 것이며, 프레임 복제 자체가 더 많은 실제 프레임보다 우수하다는 증거는 아닙니다.** 우리 실험도 여러 요소를 함께 바꿨으므로, 성능 변화가 timestamp 표현 때문인지 움직임 정보 감소 때문인지는 분리해서 판단할 수 없습니다.

```

[f0, f0, f2, f2, …]
          ↓ video_processor로 픽셀 패치 생성
          ↓ 반환 필드를 image 입력 형태로 변환

          ↓

```

여기서 **처음의 2 FPS는 디코딩 단계의 설정**입니다. 실제로 남는 서로 다른 프레임은 약 1 FPS이고, 최종 입력에는 `video_grid_thw`나 `second_per_grid_ts`를 전달하지 않습니다.

|---|---|
| 이미지 한 장 | 같은 이미지를 복제한 `[이미지, 이미지]` |
| 일반 비디오 | 샘플링한 연속 두 프레임 `[f₀, f₁]`, `[f₂, f₃]`, … |

따라서 **TimeLens-7B에서 “이미지처럼 처리한다”는 건 다른 인코더로 바꾼다는 뜻이 아니야.** 같은 인코더에 넣되, 서로 다른 두 시점이 한 patch로 묶이지 않도록 각 프레임을 독립 이미지로 만들고, LLM에는 `타임스탬프 텍스트 + 이미지 토큰`을 반복해서 전달한다는 뜻이야. 전처리 내부에서 `video_processor`를 재사용하더라도 최종 전달 필드는 이미지용이야. [TimeLens-7B 전처리 구현](https://huggingface.co/TencentARC/TimeLens-7B/blob/1740e2694669a4d03549454ed4af1cd740769f4f/processing_timelens.py)

그리고 앞서 말한 **프레임 두 장을 묶는 visual encoder의 처리**와 **LLM에서 시간 위치를 표현하는 temporal MRoPE·텍스트 타임스탬프**는 서로 다른 단계야. 이 둘을 구분해야 복제 이유와 시간 표현 방식을 혼동하지 않아.
