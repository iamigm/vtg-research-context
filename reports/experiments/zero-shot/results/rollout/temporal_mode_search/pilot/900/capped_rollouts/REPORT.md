## 연산 비용과 성능 대비 비용

비용의 분모는 query·method·seed·예산 한 경우다. seed42·43을 query 안에서 먼저 평균한다. 진행 중 비교는 3방법×4예산×2seed가 모두 완료된 같은 query만 사용한다. 다음 두 비용을 구분한다.

**Independent trace work**는 저장된 token ID·분기 prefix·judge prompt를 따라 fresh video KV와 빈 distribution/prompt cache에서 greedy → main K회 → 해당 K의 judge → tail K회만 실행하는 경우의 연산 횟수를 재구성한다. 다른 method·seed·작은 예산 judge의 cache를 빌려 쓰지 않는다. 영상 prefill은 한 번 포함한다. 이는 시간 실측이나 FLOPs 추정이 아니며 실제 native forward 계측과 대조한다. Tail이 중간 main에 영향을 주지 않는 고정 draw stream을 사용한다.

- `decoder inputs`: native decoder forward에 실제 투입하는 token position 수의 합. 재생한 prefix, judge text prefill·근거 생성, 영상 prefill 뒤의 multimodal decoder positions를 포함한다. sampling 횟수나 출력 token 수와 다르다.
- `forwards`: native model forward 호출 수. 하나의 긴 judge text prefill도1회이므로 token 수와 함께 해석한다.
- `attention pairs`: 각 forward의 causal query-key position 쌍 `q(k−q)+q(q+1)/2`의 합. q는 새 input 길이,k는 전체 KV 길이다. layer/head 곱을 생략한 context 길이 workload proxy이며 정확한 FLOPs가 아니다. vision encoder의 별도 연산은 포함하지 않는다.
- `operational`: video prefill+greedy+main+judge. `research total`: operational+진단용 tail. Tail을 후보로 쓰지 않아도 이번 실험의 총비용에서 제외하지 않는다.
- `greedy ×`: 같은 query의 video prefill+greedy 대비 decoder inputs 또는 forward 호출 수 배율. 원래 입력의 hash와 greedy ID가 동일하다. 입력 prefill과 추가 text 비용도 분리한다.

**Observed execution**은 지금 사용하는 worker3개·공유 cache의 nested sweep에서 각 main/tail/judge 구간의 wall seconds,native forward CUDA stream seconds,forward 수,decoder inputs,process별 peak allocated/reserved memory를 기록한다. CUDA events를 각 forward 전후에 배치하며 GPU 동시 실행·queue 대기의 영향을 받을 수 있다. CUDA stream seconds는 GPU 전체 사용시간이나 정확한 kernel active time이 아니다. wall−forward wall은 Python/cache/mode grouping 등 host-side 잔여시간의 근사다. peak memory는 worker별 model/KV를 포함하고 다른 worker의 점유량과 합산한 장치 전체 peak가 아니다.

Observed main/tail은 해당 K까지의 누적,judge는 해당 K의 구간이다. `sweep`은 이전 모든 작은 예산 judge를 포함한 phase 합계이고,`sweep_elapsed_seconds`는 이전 checkpoint 저장과 phase 밖 Python 처리까지 포함한 경과시간(현재 checkpoint 저장 직전)이다. 독립 K 실행시간으로 부르지 않는다. method 실행 순서·이미 저장된 cache·재개에 따라 관측 비용이 달라지므로 method 공정 비교는 independent trace work를 사용한다. 재개 실행의 재탐색·실패 비용은 누적 실행 로그와 raw actual_cost에 보존한다. 계측 도입 이전 checkpoint의 실측은 결측으로 남기며0초로 처리하지 않는다.

효율 지표는 greedy 대비 `ΔmIoU(pp)=100×mean(IoU−IoU_greedy)`,추가1,000 decoder inputs당 향상 `ΔmIoU(pp)/(mean(extra decoder inputs)/1000)`다. 음수는 비용을 써도 성능이 악화됐다는 뜻이다. `marginal Δ`와 `추가 비용`은 같은 query에서 직전 절반 예산 대비 값이다. 같은 query 집합에서 더 낮은 비용·같거나 높은 mIoU의 다른 조건이 있으면 dominated로 표시한다. 평균 개선만으로 연구적 기여를 단정하지 않으며 비용 배율,실측 시간,seed·dataset별 결과와 불확실성을 함께 본다.

### Exact prefix KV cache

생성의 input·token distribution·RNG·draw stream·mode·judge prompt는 유지한다. 한 query 안에서 이미 계산한 prefix의 CPU logits와 token별 KV를 재사용한다. 영상 KV는 한 번만 별도 참조하고 text KV는 token당 한 개를 저장하며 최대4,096 prefix로 제한한다. cache가 가득 차면 추가 prefix는 기존 native replay를 사용한다. judge text prefill과 관측 근거 생성은 기존 경로를 유지한다.

현재 independent trace work는 이 prefix cache를 fresh 상태로 시작했을 때의 native forward 횟수다. 과거 query에도 같은 trace의 최적화된 연산 횟수를 재구성한다. 기존 single-KV replay 횟수는 `single_kv_reference`로 함께 보존하며 같은 query·method·seed·예산에서 비교한다. cache 저장·복원 kernel은 decoder forward가 아니므로 decoder inputs/attention pairs에는 더하지 않고 별도 CUDA 시간과 memory로 실측한다.

실측은 `single_kv_replay`와 `prefix_kv_cache`를 구분한다. 두 구현의 서로 다른 query 평균으로 가속률을 계산하지 않는다. 기본 실측 표는 prefix cache의 모든24개 checkpoint가 완료된 공통 query만 사용한다. 기존 구현의 실측은 아래 별도 표와 원자료에 남긴다. CUDA forward 시간에 cache copy 시간이 포함되지 않으므로 cache CUDA 시간도 함께 읽는다. 본문 peak memory에는 prefix cache를 포함한다. 같은 입력으로 두 구현을 실행한 calibration의 가속률은 제한된3 query 결과이며 전체 pilot 가속률을 보장하지 않는다.

worker3개의 CUDA 실행은 이 실험 전용 pipe의 NVIDIA MPS를 사용한다. 서로 다른 process의 kernel 실행을 겹칠 수 있는 실행 서비스이며 모델·입력·dtype·rollout 정책은 바꾸지 않는다. [NVIDIA MPS 설명](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html). 동일3 client·8,192 context·client당80 native single-token forward의 microbenchmark는 실험 전체 가속률과 구분한다. MPS 전후 전체 logits byte hash와 세 데이터셋의 기존 분포·경로·judge 기록을 대조한다. 기존 kernel replay 비용과 새 MPS+prefix cache 실측은 합산하지 않는다.

### 그래프1·2·3: 더 많이 탐색하면 좋은 후보와 좋은 답이 함께 늘어나는가?

아래 그림에는 왼쪽부터 세 그래프가 있다. **같은 평가를 서로 다른 탐색 방법에 각각 적용한 것**이다. 각 그래프 안의 색은 평가값을 구분하며 회색 선은 greedy 기준이다.

| 그래프 | 제목 | 무엇을 우선 탐색하는 방법인가? |
|---|---|---|
| 1 · 왼쪽 | probability | 모델이 그 prefix와 token을 선택할 확률이 높고,조사 비용이 낮은 분기 |
| 2 · 가운데 | token_entropy | 위 조건에 더해,다음 token 확률이 여러 대안으로 흩어져 있는 분기 |
| 3 · 오른쪽 | temporal_mode | 위 조건에 더해,유효한 새 시간 가설을 발견할 전망이 있는 분기 |

**가로축은 조사 횟수의 상한이다.** 32·64·128·256은 query·방법·seed 한 경우의 main+tail 총 rollout 상한이다. 예를 들어256이면 main128회와 진단용 tail128회다. 서로 다른 후보256개라는 뜻은 아니며 중복·무효 생성도 시도 수에 포함한다. Judge 호출은 이 횟수에 넣지 않는다. 오른쪽 한 칸마다 상한이 두 배가 되므로 칸 간격이 같아도32→64와128→256의 증가량은 다르다.

**세로축은 최종 interval이 GT와 얼마나 겹치는지의 평균(mIoU)이다.** 1에 가까울수록 좋다. 0.5는 전체 query에서 interval 겹침 점수의 평균이0.5라는 뜻이며,정답률50%라는 뜻이 아니다. 세 그래프는 같은0–1 눈금을 사용한다. 각 query의 seed42·43을 먼저 평균하고 query들을 평균한다.

| 선의 색·모양 | 그림의 범례 | 쉽게 읽는 뜻 | 실제 모델 성능인가? |
|---|---|---|---|
| 파란 실선 | Selected | 모델이 마지막에 실제로 고른 답의 평균 IoU | **그렇다. 성능 개선 여부는 이 선을 본다.** |
| 초록 파선 | Main oracle | 찾은 모든 main interval 중 GT에 가장 잘 맞는 것을 사후에 골랐다면 얻는 평균 | 아니다. 탐색으로 확보한 기회의 상한이다. |
| 황갈색 점선 | Judge pool oracle | 모델에게 실제 전달한 대표 interval 중 GT에 가장 잘 맞는 것을 사후에 골랐다면 얻는 평균 | 아니다. Shortlist 안에 남은 기회의 상한이다. |
| 회색 일점쇄선 | greedy | 동일 입력의 greedy 단일 응답 mIoU | 모든 성능 비교의 기준이다. |

![그래프1·2·3: 예산별 최종 선택과 oracle](../../../../../../artifacts/runs/rollout/temporal_mode_search/pilot/900/capped_rollouts/web/budget_oracle.png)

**읽는 순서는 초록 → 황갈색 → 파랑이다.** 먼저 좋은 후보를 발견했는지,그 후보가 judge에 전달됐는지,judge가 실제로 골랐는지를 순서대로 본다. 같은 가로 위치에서 초록과 황갈색 사이의 틈은 shortlist에서 잃은 기회이고,황갈색과 파랑 사이의 틈은 최종 선택에서 잃은 기회다. 이 값은 query마다 최고점을 구한 뒤 평균한 것이며,모든 query에 공통인 하나의 정답 후보가 있다는 뜻은 아니다.

**초록만 오르고 파랑이 그대로라면 “좋은 대안은 더 찾았지만 실제 답은 좋아지지 않았다”고 읽는다.** 후보가 늘어도 상위6 mode와 대표 interval이 바뀔 수 있어 황갈색 선은 내려갈 수 있고,모델의 선택도 바뀌므로 파란 선 역시 내려갈 수 있다. 선을 연결한 것은 네 예산의 변화를 보기 위한 것이며 중간 예산을 모두 실험한 것은 아니다. Tail을 포함한 diagnostic oracle은 표에만 있고,이 세 선에는 포함하지 않는다.

#### 이 pilot의 숫자로 읽어 보기

- **그래프1 · probability:** greedy 기준 mIoU는0.5195다. 총 rollout 상한32에서 실제 선택 mIoU는0.5262(greedy 대비+0.66pp), 상한256에서는0.5229(greedy 대비+0.34pp, 개선)다. 최대 예산의 main oracle은0.7765, judge 후보 oracle은0.6870다.
- **그래프2 · token_entropy:** greedy 기준 mIoU는0.5195다. 총 rollout 상한32에서 실제 선택 mIoU는0.5289(greedy 대비+0.94pp), 상한256에서는0.5273(greedy 대비+0.78pp, 개선)다. 최대 예산의 main oracle은0.7801, judge 후보 oracle은0.6878다.
- **그래프3 · temporal_mode:** greedy 기준 mIoU는0.5195다. 총 rollout 상한32에서 실제 선택 mIoU는0.5266(greedy 대비+0.71pp), 상한256에서는0.5265(greedy 대비+0.70pp, 개선)다. 최대 예산의 main oracle은0.7826, judge 후보 oracle은0.6880다.

모든 성능 변화는 **같은 query의 greedy 대비**다. Δpp=100×(선택 mIoU−greedy mIoU)이며 양수일수록 좋다. 예를 들어0.01 차이는1pp다.

### 그래프4: 정확도를 조금 높이는 데 계산은 얼마나 더 필요한가?

앞의 세 그래프는 가로축을 생성 시도 수로 맞췄다. 네 번째 그래프는 **같은 시도 수라도 응답 길이와 후보 비교량에 따라 계산이 다를 수 있으므로,실제 처리할 token position 수를 기준으로 다시 배치한 그림**이다.

![그래프4: 전체 샘플의 성능과 연산 비용](../../../../../../artifacts/runs/rollout/temporal_mode_search/pilot/900/capped_rollouts/web/performance_cost.png)

**가로축은 query·방법·seed·예산 한 경우를 독립 실행할 때 필요한 decoder inputs의 query 평균이다.** 숫자가 클수록 모델에 더 많은 token position을 처리시킨다는 뜻이다. 출력 문장의 token 수나 GPU seconds가 아니다. 영상 prefill,greedy,main 탐색,judge 비교,진단용 tail까지 포함한 research total이다. 저장된 trace를 빈 cache에서 실행하는 기준으로 재구성하며,다른 방법·seed·작은 예산에서 계산한 cache를 공짜로 빌려 쓰지 않는다. Vision encoder의 모든 연산까지 나타내는 FLOPs 측정은 아니다.

**세로축은 모델이 실제 고른 답의 평균 IoU다.** 앞의 세 그래프의 파란 Selected 선과 같은 종류의 점수다. Oracle 선은 없다. 네 번째 그림의 세로축은 값 차이를 보기 위해 자동으로 범위를 잡으므로,0부터1까지 고정된 앞의 세 그래프와 선의 기울기나 높이를 눈대중으로 직접 비교하지 않는다.

**여기서는 색의 뜻이 바뀐다.** 앞의 세 그래프는 색으로 평가값을 구분했지만,그래프4는 색으로 탐색 방법을 구분한다.

| 색·표시 | 의미 |
|---|---|
| 파란 선 | probability 방법의 실제 최종 성능과 계산량 |
| 황갈색 선 | token_entropy 방법의 실제 최종 성능과 계산량 |
| 초록 선 | temporal_mode 방법의 실제 최종 성능과 계산량 |
| 회색 점 greedy | 추가 탐색·후보 judge 없이 greedy 답 하나를 생성한 기준 |
| 각 점 옆의32·64·128·256 | 그 점을 얻을 때의 main+tail 총 rollout 상한. Query 수나 계산량 값 자체가 아니다. |

**같은 높이라면 왼쪽 점이 더 적은 계산으로 같은 성능을 낸다. 같은 가로 위치라면 위쪽 점이 더 정확하다.** 한 점이 다른 점보다 오른쪽에만 있고 위로 올라가지 않았다면,이 비용 지표상 계산만 늘고 정확도는 좋아지지 않은 것이다. 선이 거의 수평으로 오른쪽으로 뻗으면 추가 계산의 이득이 작다는 뜻이다. greedy 회색 점보다 위에 있는지와,그만큼 오른쪽으로 얼마나 이동했는지를 함께 본다. Tail은 답에 사용하지 않았어도 이번 연구에 쓴 계산이므로 비용에 포함한다.

#### 이 pilot의 비용·정확도 예시

## 사례 탐색과 mode 비교

사례 필터는 현재 선택한 방법·seed·예산의 query별 결과를 사용한다. 비교 기준은 같은 입력의 greedy 단일 응답이다. IoU는 GT와 예측 interval의 교집합 길이 / 합집합 길이이며 범위는 0–1이고 높을수록 좋다. ΔIoU = 해당 값 − greedy IoU이며 0.01은 1pp다. Main oracle과 judge 후보 oracle은 각각 발견한 모든 main interval과 judge에 전달한 대표 interval의 최고 IoU다. Diagnostic oracle은 tail까지 포함한 최고 IoU다. Oracle은 사후 상한이며 GT는 생성·선택에 사용하지 않는다.

| 특수 기준 | query별 조건 |
|---|---|
| 회복 | greedy IoU < 0.5, 최종 선택 IoU ≥ 0.5 |
| 개선 / 악화 | 최종 선택의 greedy 대비 ΔIoU ≥ 0.01 / ≤ −0.01 |
| 후보 발견 후 선택 실패 | greedy IoU < 0.5, main oracle ≥ 0.5, 최종 선택 IoU < 0.5 |
| 탐색 후에도 미회복 | greedy IoU < 0.5, main oracle < 0.5 |
| 여러 mode | main mode 수 ≥ 2 |
| Tail에만 회복 후보 | greedy IoU < 0.5, main oracle < 0.5, diagnostic oracle ≥ 0.5 |
| 최종 선택 무효 | 유효한 최종 interval이 없음 |

수치 범위는 greedy IoU, greedy 대비 ΔIoU, main mode 수에 적용하며 양 끝을 포함한다. 모든 조건을 동시에 적용한다. Query 수는 현재 cohort의 고유 query 수이며 seed 응답 수나 영상 수가 아니다. 표본별 목록은 canonical 응답을 복제하지 않고 기존 query 지표를 조회한다.

Mode 비교는 저장된 checkpoint의 소속을 그대로 보여준다. 새 interval은 기존 mode의 **모든 interval**에 대해 IoU ≥ 0.5이고 시작·끝 차이가 각각 max(1 s, 0.1 × 두 interval 중 짧은 길이) 이내이면 통합한다. 해당 mode가 여러 개면 endpoint 거리와 mode ID 순서로 결정한다. 조건을 만족하는 mode가 없으면 새 mode다. Mode ID는 해당 방법·seed·예산 안에서만 유효하며 실제 사건 수나 정답 확률을 뜻하지 않는다. 무효 경로는 mode에 넣지 않는다. 같은 sequence의 반복은 관측 횟수로 묶고 각 고유 응답의 mode, interval, IoU와 greedy 대비 ΔIoU를 표시한다. 공통 시간축의 얇은 막대는 각 고유 interval이며 mode 전체를 하나의 합친 interval로 해석하지 않는다.
