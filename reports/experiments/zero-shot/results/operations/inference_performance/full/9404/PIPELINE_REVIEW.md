# worker 증설 이후 GPU 사용률 하락 원인과 개선안 · 전체 full9404 추론 진단

## 결론

영상 디코딩·크기 조정의 CPU 비용은 여전히 남아 있다. 하지만 현재의 간헐적인 GPU 휴지를 전부 CPU 전체 처리 능력 부족으로 설명할 수는 없다. 입력 처리 시간의 편차와 순서 보장 대기, 그리고 생성 중 확률 계측의 GPU→CPU 동기화를 분리해서 봐야 한다. 이번 조사에서는 실행 설정을 추가 변경하지 않았다.

디코딩은 압축된 MP4를 이미지 프레임의 픽셀로 풀어 읽는 것이다. 모델 입력에 필요하며 원본 파일을 재인코딩하거나 수정하지 않는다. HTML용 H.264 사본을 만드는 작업과는 다르다.

## 관측 사실

모델별 worker 4개로 실행 중에 약 31초 동안 60회 측정했다.

| 항목 | 관측값 |
|---|---:|
| GPU 평균 사용률 | 68.0% |
| GPU 사용률 중앙값 | 98.0% |
| GPU 사용률 10% 이하 | 60회 중 15회 |
| cgroup 평균 CPU 사용량 | 7.76코어 |
| CPU 할당량 | 12코어 |
| CPU 제한이 발생한 구간 | 313구간 중 15구간 |

nvidia-smi 사용률은 내부 집계값이므로 각 관측치를 독립된 순간 측정으로 보거나 정확한 GPU idle 시간 비율로 바꾸면 안 된다. 관측 구간에 따라 평균도 달라진다. 앞선 변경 후 처리량 측정에서는 평균 75.8%였다.

최근 200개 완료 응답의 파일 저장 시각 간격에서 기록된 생성 시간을 뺀 값:

| 모델 | 초당이 아닌 응답당 시간(초) | 생성 구간 비중 | 생성 외 대기 중앙값(초) | 95백분위(초) | 최대(초) |
|---|---:|---:|---:|---:|---:|
| Qwen2.5 | 4.10 | 43.6% | 0.01 | 14.58 | 38.86 |
| Qwen3 | 3.34 | 55.1% | 0.01 | 8.20 | 22.73 |

생성 외 시간에는 DataLoader 대기, GPU 입력 전송, 기준선 읽기, 결과 쓰기 등이 함께 들어간다. GPU 사용률 표와 정확히 같은 시간 구간도 아니다. 거의 즉시 다음 입력을 받다가 특정 지점에서 긴 간격이 생기는 패턴은 확인되지만, 이 차이만으로 DataLoader의 대기 시간을 직접 측정했다고 주장하지 않는다.

cgroup I/O pressure 평균은 0이었다. 시스템 전체 메모리 여유 대신 컨테이너 제한을 확인했으며, 제한은 160GiB다. 측정 시 사용량 약 115GiB 중 상당 부분은 파일 캐시였고 익명 메모리는 약 19.5GiB였다. 해당 수치만으로 디스크 지연이 전혀 없다고 단정하지 않지만, 지속적인 디스크 포화나 VRAM 용량 부족을 주원인으로 볼 근거는 없다.

## 원인별 구분

### 1. CPU 디코딩·resize: 직접 프로파일로 확인

이전 입력 준비 프로파일에서 Qwen2.5는 디코딩 약 56%, resize 약 32%; Qwen3는 디코딩 약 62%, resize 약 29%였다. 소수의 대표 샘플에 대한 값이며 전체 평균은 아니다. 긴 영상과 프레임 의존성이 많은 영상은 전처리 시간이 길어질 수 있다.

### 2. 순서 보장으로 인한 대기: 코드상 존재하며 현재 양상과 부합

현재 DataLoader는 `in_order=True` 기본값이고, 모델별 worker 4개와 `prefetch_factor=2`로 최대 8개 작업을 미리 요청한다. PyTorch 구현은 다음으로 반환할 인덱스가 준비될 때까지, 먼저 끝난 다른 인덱스의 결과를 보관한다. 따라서 느린 샘플 하나 때문에 준비된 뒤쪽 샘플을 GPU에 공급하지 못할 수 있다. 이는 head-of-line blocking이다.

현재 worker별 관측 CPU 사용량이 약 0.46~1.12코어로 불균일하고, 전체 CPU는 할당량 아래인데 GPU가 간헐적으로 비는 점도 이 가설과 부합한다. 다만 현재 실행에서 ready queue와 각 작업의 완료 시각을 직접 계측하지 않았으므로 발생 횟수와 전체 대기 중 비율은 아직 모른다.

### 3. 동일 영상 반복 처리: manifest로 확인

조사 시점의 남은 입력 중 Qwen2.5는 3,746개 질의에 영상 2,129개, Qwen3는 4,082개 질의에 영상 2,238개였다. 같은 모델 안에서도 각각 1,617회·1,844회의 추가 영상 접근이 발생한다. 현재 `Prepared`는 샘플마다 영상 입력을 준비하며, Qwen3의 캐시는 한 샘플의 두 prompt 순서 사이에서만 재사용된다. 여러 질의와 worker 사이의 영상 캐시는 없다.

반복 접근 수가 곧 절약 가능한 전체 실행 시간은 아니다. OS 파일 캐시는 압축 파일 읽기를 줄여도 디코딩·resize 결과를 재사용하지 않는다.

### 4. 확률 계측의 CPU 동기화: 코드에서 확인, 시간 비중은 미측정

매 생성 step에서 raw·processed 확률을 계산하고 `.tolist()`, `float(cuda_tensor)`, `int(cuda_tensor)`를 여러 번 호출한다. 이는 GPU 결과를 CPU에서 읽도록 하므로 CUDA 작업의 완료를 기다린다. 토큰 디코딩·Python dict 생성도 step마다 실행된다. GPU의 짧은 계산 사이에 빈 구간을 만들 수 있다.

이 비용은 기록된 `elapsed_seconds`의 생성 구간 안에 포함된다. 따라서 생성 외 20~39초 간격의 직접 원인으로 동일시하면 안 된다. 생성 자체의 개선 후보로 별도 측정해야 한다.

## 개선 우선순위

| 순위 | 변경안 | 목적 | 검증 조건 |
|---|---|---|---|
| 1 | 준비 완료 순서로 공급하는 `in_order=False` 소규모 비교 | 느린 샘플 때문에 뒤의 준비된 샘플까지 기다리는 현상 완화 | 같은 샘플 집합에서 입력 ID·프레임 시각·영상 tensor·생성 ID 비교. 결과 저장은 sample_key 기준 유지 |
| 2 | 제한된 크기의 공유 영상 전처리 캐시 | 같은 영상을 질의마다 다시 디코딩·resize하는 비용 감소 | 파일 식별자, 프레임 인덱스, reader 버전, resize 설정을 cache key에 포함하고 출력 tensor 비교 |
| 3 | 계측 tensor를 GPU에 모았다가 샘플 생성 후 CPU로 한 번에 이동 | 토큰마다 발생하는 동기화와 Python 작업 감소 | 선택 토큰, raw·processed top-30 및 전체 어휘 엔트로피 일치 |
| 4 | 측정 결과에 따라 prefetch와 GPU 전송 중첩 조정 | 짧은 공급 공백과 전송 대기 완화 | host 메모리·준비 대기열·전송 시간을 함께 확인 |

worker를 무조건 더 늘리는 것은 우선순위가 낮다. 지금은 12코어 할당 안에서 순서 보장·작업 편차를 먼저 해결할 여지가 있다. prefetch만 크게 늘리면 준비된 큰 tensor를 더 오래 보관할 수 있고, 순서 보장 대기 자체는 남는다.

캐시는 모델별 전처리 차이를 반드시 구분해야 한다. 현재 Qwen2.5의 pixel budget은 downsample rate 28, Qwen3는 32를 사용하고 Qwen3에는 image_patch_size=16도 전달한다. 같은 영상이라는 이유만으로 두 모델의 resize된 tensor를 공유하면 안 된다. 모델 간 공유는 실제 frame index와 디코딩 조건이 동일함을 확인한 raw frame 단계부터 검토한다.

GPU 디코딩이나 다른 decoder로 변경하는 방안은 프레임·픽셀 값의 동일성 검증 부담이 커서 후순위다. 배치 크기 증가는 현재 `Capture`가 batch 0 하나를 가정하므로 계측 코드까지 바꿔야 한다.

## 다음 검증 절차

1. 각 샘플에 CPU 준비 시간, worker 완료 시각, main에서 입력을 기다린 시간, GPU 전송 시간, 생성 시간, 결과 저장 시간을 분리해 기록한다. 완료된 다른 입력이 있는지도 계측한다.
2. 새로운 검증용 출력 경로에서 동일 샘플·동일 모델·동일 생성 조건으로 순서 보장 여부만 바꿔 비교한다. 서로 다른 영상 구간의 처리량 비교로 대체하지 않는다.
3. sample_key 기준 누락·중복, 입력 tensor, 입력 ID, 생성 ID와 엔트로피가 일치할 때만 본 실행 적용을 검토한다.
